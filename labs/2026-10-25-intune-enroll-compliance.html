Enroll a Windows VM in Intune and Fix a Noncompliant Device

Track: Intune · Builds on Lab 02 (Entra ID users and Graph PowerShell)
⏱ 25–30 min Level: Entry Skill: endpoint management & compliance troubleshooting

The ticket

INC-0057 · Priority: P2
From: Dana (Sales) <dana@contoso.lab>
“IT set up my new laptop yesterday, but now Outlook says my device doesn't meet the organization's requirements and I can't get to email. Company Portal shows a red X. Help!”

This is one of the most common Intune tickets out there. Today you play both sides: you enroll a Windows VM, deliberately break compliance with a policy, then troubleshoot it the way you would on a real call, from the admin center, from the device, and from Graph PowerShell.

Prerequisites (all free)

  • Your test tenant from Lab 02. Intune needs a license: the M365 Developer Program E5 sandbox includes it, or start the free 30-day Microsoft Intune trial on a free Entra tenant. Never a school or work tenant.
  • A test user with an Intune (or E5) license. Your admin account is fine for a lab.
  • A Windows 11 Enterprise evaluation VM (free 90-day ISO from the Microsoft Evaluation Center) in Hyper-V or VirtualBox. Home edition can't join Entra ID. Take a snapshot/checkpoint first.
  • PowerShell 7 with the Microsoft.Graph module (installed in Lab 02).
⚠ Check one setting before you start: intune.microsoft.com > Devices > Enrollment > Windows > Automatic Enrollment. Set MDM user scope to All (or a group your user is in). If this is “None”, the device joins Entra but never shows up in Intune, which is itself a classic ticket.

Steps

In the Intune admin center: Devices > Compliance > Create policy, platform Windows 10 and later. Name it LAB03-Win-Baseline. Under Device Properties set Minimum OS version to 10.0.99999.0 (no real build is this high, so it will fail). Under System Security set Firewall to Require. Leave Actions for noncompliance at the default (mark noncompliant immediately). Assign to All users or your test user, then create it.

On the VM: Settings > Accounts > Access work or school > Connect, then click Join this device to Microsoft Entra ID (the small link at the bottom). Sign in as your test user and confirm. Sign out and back in as that user (user@yourtenant.onmicrosoft.com).

dsregcmd /status | Select-String "AzureAdJoined|DomainJoined|TenantName|MdmUrl|AzureAdPrt"

You want AzureAdJoined : YES, your tenant name, and an MdmUrl pointing at enrollment.manage.microsoft.com. No MdmUrl means auto-enrollment scope is wrong (see the warning above).

Settings > Access work or school > click the account > Info > Sync. Then, in an admin PowerShell on the VM:

Get-WinEvent -LogName "Microsoft-Windows-DeviceManagement-Enterprise-Diagnostics-Provider/Admin" -MaxEvents 15 |
  Select-Object TimeCreated, Id, LevelDisplayName, Message | Format-List

This log is where enrollment and policy errors land. Note any Error-level entries and their IDs.

From your lab admin box (PowerShell 7):

Connect-MgGraph -Scopes "DeviceManagementManagedDevices.ReadWrite.All","DeviceManagementManagedDevices.PrivilegedOperations.All","DeviceManagementConfiguration.Read.All"

Get-MgDeviceManagementManagedDevice |
  Select-Object DeviceName, UserPrincipalName, OperatingSystem, OsVersion, ComplianceState, LastSyncDateTime |
  Format-Table -AutoSize

Compliance can take 5–15 minutes to evaluate. You'll likely see unknown or inGracePeriod first, then noncompliant. Grab a coffee, or keep going and come back.

Admin center: Devices > All devices > (your VM) > Device compliance > LAB03-Win-Baseline. You should see Minimum OS version flagged with the actual build next to it. Also check the user's view: open Company Portal on the VM and click the device; it lists the same failing setting in plain English. That's the screen Dana is looking at.

# On the VM: what build is it really?
[System.Environment]::OSVersion.Version
Get-NetFirewallProfile | Select-Object Name, Enabled

The device is fine; the policy is wrong. Edit LAB03-Win-Baseline and change Minimum OS version to a real baseline your VM meets, e.g. 10.0.22621.0 (Windows 11 22H2). Save. Then push a sync from Graph instead of waiting:

$dev = Get-MgDeviceManagementManagedDevice -Filter "deviceName eq 'YOUR-VM-NAME'"
Sync-MgDeviceManagementManagedDevice -ManagedDeviceId $dev.Id
# On the VM (admin) - lab only!
Set-NetFirewallProfile -Profile Domain,Public,Private -Enabled False
# Sync from Settings, wait, re-check compliance... then fix:
Set-NetFirewallProfile -Profile Domain,Public,Private -Enabled True

Now the device is the problem, not the policy. Knowing which side to fix is the whole skill.

Verify it worked

Write the ticket note (2 minutes)

Practice closing INC-0057 in three lines: Cause (compliance policy had an unreachable minimum OS version), Fix (corrected baseline to 10.0.22621.0, forced sync), Verified (device compliant in Intune, user confirmed Outlook access). Short, factual, and something the next tech can search for.

Cleanup

# Remove the Intune record and the Entra device object
$dev = Get-MgDeviceManagementManagedDevice -Filter "deviceName eq 'YOUR-VM-NAME'"
Remove-MgDeviceManagementManagedDevice -ManagedDeviceId $dev.Id

Connect-MgGraph -Scopes "Device.ReadWrite.All"
$aad = Get-MgDevice -Filter "displayName eq 'YOUR-VM-NAME'"
Remove-MgDevice -DeviceId $aad.Id

Disconnect-MgGraph

Then delete the LAB03-Win-Baseline policy in the admin center (or keep it with the fixed value for Lab-future use), and revert the VM to the checkpoint you took. Keep the checkpoint: the next Intune lab starts from a clean, un-enrolled VM.

Interview questions

  1. What's the difference between a compliance policy and a configuration profile in Intune? (Hint: one checks and reports, the other pushes settings. Conditional Access uses the compliance result to allow or block access.)
  2. A device is Entra-joined but doesn't show up in Intune. Where do you look first? (MDM user scope under automatic enrollment, the user's Intune license, and dsregcmd /status for an MdmUrl.)
  3. A user says they're blocked from email because their device is noncompliant. Walk me through it. (Identify the device, read the failing setting, decide device-side vs. policy-side fix, sync, verify, document.)

Stretch goal (optional)

Create a Settings catalog configuration profile (Devices > Configuration > Create > Windows 10 and later > Settings catalog) that sets a lock-screen message or disables the Windows consumer features, assign it, and confirm it applied with mdmdiagnosticstool.exe -out C:\Temp\MDMDiag (open the HTML report it generates). Bonus: export the device list to CSV with Graph and Export-Csv.
