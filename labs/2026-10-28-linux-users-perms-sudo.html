Linux Users, Shared Folders & Least-Privilege sudo

Track: Linux admin · The Linux mirror of Lab 01 (AD onboarding) and Lab 02 (offboarding), on a disposable Ubuntu box
⏱ 25–30 min Level: Entry+ Skill: useradd/chage, groups, chmod & setgid, ACLs, sudoers, offboarding

The ticket

INC-1106 · Priority: P3
From: Priya Shah (Marketing) <pshah@contoso.lab>
“Day one and I can't save anything to the marketing folder on filesrv01, it just says Permission denied. Also my manager says Tom left and asked if you can make sure he can't get in anymore. Oh, and can the help desk reset our passwords without bugging the Linux guy?”

Three tickets in one, which is very realistic. You'll onboard users, fix a broken shared folder (twice, because the first fix reveals a second bug), set up a least-privilege sudo rule for Tier 1, and offboard a leaver without destroying their files. Same lifecycle you did in AD and Entra, now on Linux.

Prerequisites (all free)

  • Docker on any lab host (Docker Desktop, or Docker on your Pi). The ubuntu:24.04 image is free and runs on ARM and x86.
  • No Docker handy? A free Ubuntu Server 24.04 VM in Hyper-V or VirtualBox works identically; just snapshot it first.
  • Comfort with a bash prompt. That's it.

Safety: run everything inside the lab06 container (prompt shows root@filesrv01). Do not run these commands directly on your Pi host; it runs Pi-hole, Vaultwarden, and friends, and a bad sudoers file there is a bad afternoon.

Steps

Everything happens inside a disposable Ubuntu container, so nothing on your Pi or PC changes. Run this from Docker Desktop's terminal or any Docker host in your lab:

docker run -it --rm --name lab06 --hostname filesrv01 ubuntu:24.04 bash

You're now root inside the container. Install the few tools the base image leaves out:

apt-get update && apt-get install -y sudo acl
cat /etc/os-release | head -2

Create the team group, then the users with home directories, a bash shell, a full name in the comment field, and group membership:

groupadd marketing
useradd -m -s /bin/bash -c "Priya Shah" -G marketing pshah
useradd -m -s /bin/bash -c "Tom Lee"   -G marketing tlee
echo 'pshah:Welcome-Lab06!' | chpasswd
echo 'tlee:Welcome-Lab06!'  | chpasswd
✓ Verify: id pshah lists marketing, getent group marketing shows both users, and chage -l pshah shows the password details. (In production you'd also run chage -d 0 pshah to force a change at first login. We'll do that in step 8, because it would make every su - pshah test below stop and demand a new password.)

Build the share the way someone rushed it into production, then test as Priya. su - user -c runs one command as that user without needing their password, because you're root.

mkdir -p /srv/marketing
ls -ld /srv/marketing
su - pshah -c 'touch /srv/marketing/q4-plan.txt'
✓ Verify: You get Permission denied. Read the ls -ld output: owner root, group root, mode drwxr-xr-x. Priya is “other”, and other has no write bit. That's your root cause.
chgrp marketing /srv/marketing
chmod 2770 /srv/marketing
ls -ld /srv/marketing
su - pshah -c 'echo "Q4 launch ideas" > /srv/marketing/q4-plan.txt'
ls -l /srv/marketing

2770 means setgid (2), owner rwx (7), group rwx (7), other nothing (0). The setgid bit on a directory makes new files inherit the directory's group instead of the creator's primary group.

✓ Verify: The directory shows drwxrws--- (note the s), and q4-plan.txt is group marketing, not pshah.
su - tlee -c 'echo "add webinar" >> /srv/marketing/q4-plan.txt'

Denied again. Run ls -l /srv/marketing: the file is -rw-r--r--, because Priya's umask (022) stripped group write. Classic “I can open it but can't save it” ticket. Fix the existing file, then add a default ACL so every future file is group-writable regardless of anyone's umask:

setfacl -m g:marketing:rw /srv/marketing/q4-plan.txt
setfacl -m g:marketing:rwx /srv/marketing
setfacl -d -m g:marketing:rwx /srv/marketing
getfacl /srv/marketing

If setfacl says Operation not supported, your Docker storage doesn't support ACLs; repeat this lab in an Ubuntu Server VM instead, or use the fallback chmod g+w on the file and set umask 002 in each user's ~/.profile.

✓ Verify: getfacl shows a default:group:marketing:rwx line. Then run su - tlee -c 'echo "add webinar" >> /srv/marketing/q4-plan.txt' (works now) and su - tlee -c 'touch /srv/marketing/budget.txt', then su - pshah -c 'echo edit >> /srv/marketing/budget.txt'. Both succeed, and ls -l shows a + after the mode bits, meaning an ACL is present.

Tier 1 should be able to reset user passwords and check expiry, but not become root. Create a tech account and a sudoers drop-in, and always syntax-check it before it goes live; a broken sudoers file can lock out every admin.

groupadd helpdesk
useradd -m -s /bin/bash -G helpdesk hdtech
echo 'hdtech:Tier1-Lab06!' | chpasswd

cat > /etc/sudoers.d/helpdesk <<'EOF'
# Tier 1: reset passwords for normal users and read expiry info only
%helpdesk ALL=(root) /usr/bin/passwd [a-z]*, !/usr/bin/passwd root, /usr/bin/chage -l *
EOF
chmod 440 /etc/sudoers.d/helpdesk
visudo -cf /etc/sudoers.d/helpdesk
✓ Verify: visudo prints parsed OK. Then test as the tech (sudo asks for hdtech's password, Tier1-Lab06!):
su - hdtech
sudo -l                    # lists exactly the three rules
sudo chage -l pshah        # allowed
sudo passwd pshah          # allowed: set a new temp password
sudo passwd root           # denied
sudo cat /etc/shadow       # denied
sudo -i                    # denied
exit
Why it matters: Each denial is logged. On a real server you'd see them in /var/log/auth.log or journalctl _COMM=sudo, which is exactly where you look when someone says “sudo isn't working.”

HR says Tom's last day was Friday. Lock the account, expire it, kill interactive logins, remove his access, and hand his files to his manager. Don't userdel -r on day one; legal or the team may need his data.

usermod -L tlee                       # lock the password
chage -E 0 tlee                       # expire the account
usermod -s /usr/sbin/nologin tlee     # no interactive shell
gpasswd -d tlee marketing             # remove from the share group
find /srv/marketing -user tlee -ls    # what did he own?
find /srv/marketing -user tlee -exec chown pshah {} \;
✓ Verify: passwd -S tlee shows L (locked), chage -l tlee shows the account expired, id tlee no longer lists marketing, su - tlee is refused (expired account or This account is currently not available), and find /srv/marketing -user tlee returns nothing.

Close it like a pro. Paste this into a file (or your notes app) and fill in the blanks in your own words:

cat > /root/INC-1106-resolution.txt <<'EOF'
INC-1106 | Marketing share write access | Resolved
Symptom: New hire pshah got "Permission denied" writing to /srv/marketing.
Cause: Share owned root:root 755; marketing group had no write access.
       Second issue: default umask 022 made new files read-only to teammates.
Fix: chgrp marketing + chmod 2770 (setgid), default ACL g:marketing:rwx.
Also: helpdesk sudo rule added (passwd/chage -l only), validated with visudo -c.
      tlee offboarded per HR: locked, expired, nologin, removed from group, files -> pshah.
Verified: pshah and tlee (before offboarding) could create and edit each other's files.
EOF
cat /root/INC-1106-resolution.txt
chage -d 0 pshah     # hand-off: force a new password at first real login
chage -l pshah | head -1

Interview questions

  1. A user gets “Permission denied” on a shared directory. Walk me through how you'd troubleshoot. (Check id user for group membership, ls -ld on the directory and every parent since you need execute on each one, getfacl for ACLs, then test with su - user -c. Remember a user must log out and back in before a new group membership takes effect.)
  2. What does the setgid bit do on a directory, and how is it different from a default ACL? (setgid makes new files inherit the directory's group. It doesn't change permissions. A default ACL sets the permissions new files get, overriding the creator's umask for the named entries. Shared folders usually want both.)
  3. Why edit sudoers with visudo, and what's risky about wildcards in a rule? (visudo locks the file and syntax-checks before saving, so a typo can't break sudo for everyone. Wildcards match arguments, including extra ones and spaces, so a loose rule like /usr/bin/vim * or /bin/cp * can be abused to edit or overwrite any file and escalate to root. Grant specific commands and arguments, and prefer tools that can't spawn a shell.)
