Triage a “My PC Is So Slow” Ticket on Windows 11

Track: Windows troubleshooting · Builds on Lab 03 (reuses your Windows 11 eval VM and its clean checkpoint)
⏱ 25–30 min Level: Entry Skill: performance triage, disk cleanup, event logs, SFC/DISM

The ticket

INC-0061 · Priority: P3
From: Marcus (Accounting) <marcus@contoso.lab>
“My computer has been super slow since last week. The fan is always loud, Excel takes forever to open, and I got a pop-up saying I'm low on disk space. I already restarted twice.”

“Slow PC” is the single most common desktop support ticket, and it's vague on purpose. Today you plant three real causes on your VM (a CPU hog, a startup item, and a disk filler), then find each one with the same methodical checks you'd run on a live remote session: CPU, memory, disk, startup, logs, system file health.

Prerequisites (all free)

  • Your Windows 11 Enterprise evaluation VM from Lab 03 (Hyper-V or VirtualBox). Revert it to the clean checkpoint, then take a new checkpoint called pre-lab04.
  • At least 6 GB free on the VM's C: drive (we'll fill 3–4 GB on purpose).
  • Windows PowerShell or PowerShell 7, run as Administrator inside the VM. Everything happens inside the VM, never on your real PC.

Part A: Break it (5 min)

You're the “user” for a minute. Pretend you didn't see this part when you get to Part B.

New-Item -ItemType Directory -Path C:\ProgramData\SyncHelper -Force | Out-Null
Set-Content C:\ProgramData\SyncHelper\synchelper.ps1 'while ($true) { [math]::Sqrt((Get-Random)) | Out-Null }'
Start-Process powershell.exe -WindowStyle Hidden -ArgumentList '-NoProfile -ExecutionPolicy Bypass -File C:\ProgramData\SyncHelper\synchelper.ps1'

This pins one CPU core, just like a stuck sync client or a broken updater.

New-ItemProperty -Path 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Run' -Name 'SyncHelper' `
  -Value 'powershell.exe -WindowStyle Hidden -NoProfile -ExecutionPolicy Bypass -File C:\ProgramData\SyncHelper\synchelper.ps1' -Force

That's why “I already restarted twice” didn't help.

$junk = "$env:LOCALAPPDATA\Temp\ExcelCache"
New-Item -ItemType Directory -Path $junk -Force | Out-Null
1..3 | ForEach-Object { fsutil file createnew "$junk\cache_$_.tmp" 1GB }

fsutil file createnew allocates the space instantly. Adjust the count if your VM disk is small.

Part B: Troubleshoot it (15–20 min)

Now you're the tech on a remote session. Work the checks in order and jot findings as you go; you'll need them for the ticket note.

Get-CimInstance Win32_OperatingSystem |
  Select-Object Caption, BuildNumber, LastBootUpTime,
    @{n='FreeRAM_GB';e={[math]::Round($_.FreePhysicalMemory/1MB,2)}}

Get-Volume -DriveLetter C |
  Select-Object DriveLetter, @{n='Size_GB';e={[math]::Round($_.Size/1GB,1)}},
    @{n='Free_GB';e={[math]::Round($_.SizeRemaining/1GB,1)}}

Always check uptime first. Users say “I restarted” when they mean “I closed the lid.” (Fast Startup also means Shut down isn't a real restart.)

# Live CPU % per process (sampled over 2 seconds)
Get-Counter '\Process(*)\% Processor Time' -SampleInterval 2 -MaxSamples 1 |
  Select-Object -ExpandProperty CounterSamples |
  Where-Object { $_.InstanceName -notin '_total','idle' } |
  Sort-Object CookedValue -Descending | Select-Object -First 5 InstanceName, @{n='CPU';e={[math]::Round($_.CookedValue,1)}}

# Which powershell is it, and what's it running?
Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" |
  Select-Object ProcessId, ParentProcessId, CommandLine | Format-List

The CommandLine column is the money shot: it shows the hidden script path. Cross-check in Task Manager (Ctrl+Shift+Esc > Details, add the Command line column).

Get-CimInstance Win32_StartupCommand |
  Select-Object Name, Location, User, Command | Format-List

Get-ScheduledTask | Where-Object { $_.State -ne 'Disabled' -and $_.TaskPath -notlike '\Microsoft\*' } |
  Select-Object TaskName, TaskPath, State

You should spot SyncHelper under HKU\...\Run. Also open Task Manager > Startup apps to see it the way a user would. Scheduled tasks are the other common hiding spot, so make checking both a habit.

# Biggest folders in the user's profile (top level)
Get-ChildItem $env:USERPROFILE -Directory -Force -ErrorAction SilentlyContinue | ForEach-Object {
  $sum = (Get-ChildItem $_.FullName -Recurse -File -Force -ErrorAction SilentlyContinue | Measure-Object Length -Sum).Sum
  [pscustomobject]@{ Folder = $_.Name; GB = [math]::Round($sum/1GB,2) }
} | Sort-Object GB -Descending | Select-Object -First 5

# Biggest individual files under AppData
Get-ChildItem "$env:LOCALAPPDATA" -Recurse -File -Force -ErrorAction SilentlyContinue |
  Sort-Object Length -Descending | Select-Object -First 5 FullName, @{n='GB';e={[math]::Round($_.Length/1GB,2)}}

On a real call you'd also use Settings > System > Storage or the free tool WinDirStat. Note what you find before deleting anything: it's the user's data until proven otherwise.

# Errors and criticals in the System log, last 24 hours
Get-WinEvent -FilterHashtable @{LogName='System'; Level=1,2; StartTime=(Get-Date).AddDays(-1)} -MaxEvents 20 -ErrorAction SilentlyContinue |
  Select-Object TimeCreated, Id, ProviderName, Message | Format-Table -Wrap

# Unexpected shutdowns (41 = Kernel-Power, 6008 = dirty shutdown)
Get-WinEvent -FilterHashtable @{LogName='System'; Id=41,6008} -MaxEvents 5 -ErrorAction SilentlyContinue

Then run perfmon /rel to open Reliability Monitor. It's the fastest “what changed last week?” view in Windows, and users never know it exists.

DISM /Online /Cleanup-Image /ScanHealth
sfc /scannow

Each takes a few minutes; start it and keep going in a second window. On your clean VM both should come back clean. Know the order for real tickets: if SFC finds corruption it can't fix, run DISM /Online /Cleanup-Image /RestoreHealth and then sfc /scannow again.

# Stop the hog (match on command line so you don't kill your own shell)
Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" |
  Where-Object CommandLine -like '*synchelper.ps1*' |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }

# Remove the startup entry and the script
Remove-ItemProperty -Path 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Run' -Name 'SyncHelper'
Remove-Item C:\ProgramData\SyncHelper -Recurse -Force

# Clear the junk (lab only; on a real ticket, confirm with the user first)
Remove-Item "$env:LOCALAPPDATA\Temp\ExcelCache" -Recurse -Force

For routine space recovery on real machines, cleanmgr /sageset:1 then cleanmgr /sagerun:1 (or Storage Sense) is the safe, supported way.

Verify it worked

Write the ticket note (2 minutes)

Close INC-0061 in four lines. Symptoms: slowness, loud fan, low disk warning. Cause: a hidden script (synchelper.ps1) using a full CPU core, relaunched at logon by an HKCU Run key, plus about 3 GB of stale temp files. Fix: stopped the process, removed the Run key and script, cleared temp data after confirming with the user; DISM/SFC clean. Verified: CPU idle after a fresh logon, 3 GB recovered, user confirmed Excel opens normally. Add one more line if this were real: escalated to Security to review where the script came from.

Cleanup

You already removed the planted items in step 10. To be thorough, revert the VM to pre-lab04 (or the clean Lab 03 checkpoint). Keep that clean checkpoint around: future Windows labs start from it.

Interview questions

  1. A user says their computer is slow. What do you check, and in what order? (Scope it first: everything or one app, since when, what changed. Then uptime, CPU/RAM/disk in Task Manager or Resource Monitor, free space, startup items, Reliability Monitor and event logs, updates, malware scan, SFC/DISM. Hardware last: disk health and RAM.)
  2. What's the difference between SFC and DISM, and why does the order matter? (SFC repairs protected system files from the local component store; DISM repairs that component store itself, from Windows Update or a source. If the store is broken, SFC can't fix anything until DISM runs.)
  3. Name three places a program can configure itself to start automatically. (HKCU/HKLM Run and RunOnce keys, the Startup folder in shell:startup, scheduled tasks, services. Bonus: Group Policy logon scripts, which connects back to Lab 01.)
